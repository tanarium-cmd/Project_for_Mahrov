# Тестовое задание: Отказоустойчивая система с автоматизацией

## Описание задачи

Создать отказоустойчивую систему с автоматизацией установки и настройки, включающую мониторинг через Grafana и VictoriaMetrics. Система должна обеспечивать балансировку HTTP-трафика между бэкенд-нодами, кластеризацию балансировщиков и централизованный сбор метрик.

## Архитектура системы

Система должна состоять из следующих элементов:

- Балансировщик контейнер 1 (lb1)
- Балансировщик контейнер 2 (lb2)
- Бэкэнд контейнер 1 (backend1)
- Бэкэнд контейнер 2 (backend2)
- Контейнер с автоматизацией (ansible)
- Контейнер grafana: Grafana (monitoring)
- Контейнер с VictoriaMetrics (monitoring)

---

## Описание компонентов

### Балансировщик (lb1, lb2)

**Назначение:** HTTP балансировщик трафика, состоящий из 2 нод с 1 VIP.

**Функциональность:**
- Балансировка HTTP трафика на порт 80
- Распределение трафика на бэкэнд ноду 1 и ноду 2
- Проверка доступности бэкэнда с автоматическим отключением неработающей ноды
- Экспорт метрик в формате Prometheus для сбора и визуализации в Grafana
  - Пример: `nginx_vts_server_responses{code="2xx",...}`
- Кластеризация через Keepalived или Pacemaker для обеспечения высокой доступности

**Требования:**
- 2 ноды с единым VIP-адресом
- Работа на порту 80
- Проверка доступности бэкендов и отключение неработающих нод
- Использование Nginx или аналогичного ПО
- Кластеризация через Keepalived или Pacemaker

**Реализация:** 
- Любой HTTP балансировщик (например, Nginx)
- Система кластеризации: Pacemaker или Keepalived

---

### Бэкэнд (backend1, backend2)

**Назначение:** Приложение, обрабатывающее HTTP трафик, состоящее из 2 нод.

**Функциональность:**
- Прослушивание HTTP запросов на порту 8080
- Ответ на простой GET запрос HTML страницей с контентом:
  - Бэкэнд 1: возвращает "Бэкенд 1"
  - Бэкэнд 2: возвращает "Бэкенд 2"
- Динамическое отображение в зависимости от произведённой балансировки

**Требования:**
- Работа на порту 8080
- Ответ на GET-запрос HTML-страницей с уникальным контентом
- Отсутствие кластеризации

**Реализация:**
- Любой HTTP обработчик (например, Apache или самописное приложение)
- Прослушивание порта 8080
- Кластеризация **не требуется**

---

### VictoriaMetrics

**Назначение:** Хранение и агрегирование метрик, собираемых с компонентов системы.

**Функциональность:**
- Коллектор метрик
- Сбор метрик с эндпоинтов балансировщиков и бэкенд-нод
- Сбор метрик: CPU, RAM, сеть, состояние сервисов
- Кластеризация **не требуется**

**Требования:**
- Интеграция с Grafana как источник данных
- Предустановленные дашборды в Grafana для мониторинга

**Реализация:**
- Сервер VictoriaMetrics (в контейнере мониторинга)

---

### Grafana

**Назначение:** Визуализация метрик, собранных с балансировщика HTTP трафика и инфраструктуры.

**Функциональность:**
- Подключение к VictoriaMetrics через датасорс
- Доступность по порту 3000
- Предустановленные дашборды для мониторинга:
  - Статуса балансировщиков (активный/резервный)
  - Доступности бэкенд-нод
  - Нагрузки на ноды
  - Состояния VIP-адреса
- Кластеризация **не требуется**

**Требования:**
- Интеграция VictoriaMetrics как источника данных
- Автоматический импорт предустановленных дашбордов

**Реализация:**
- Сервер визуализации метрик (в контейнере мониторинга)
- Конфиг должен содержать датасорс с настройками подключения к VictoriaMetrics

---

### Сервер автоматизации (ansible)

**Назначение:** Автоматизированная установка и настройка всех компонентов системы.

**Функциональность:**
- Содержит ПО Ansible с набором YML скриптов
- После запуска скриптов установки и настройки система должна быть полностью функциональна
- Плейбуки должны быть разделены по компонентам (последовательность запуска на ваше усмотрение):
  1. Playbook установки и настройки балансировщиков
     - Установка Nginx/аналогичного ПО
     - Конфигурация балансировки на backend1 и backend2
     - Проверка работоспособности
  2. Playbook установки и настройки кластеризации балансировщиков
     - Установка Keepalived или Pacemaker
     - Настройка VIP-адреса
     - Тестирование переключения при падении ноды
  3. Playbook установки и настройки бэкэнда
     - Установка Apache/самописного обработчика
     - Развёртывание HTML-страниц с уникальным контентом
     - Проверка ответов на GET-запросы
  4. Playbook установки и настройки мониторинга
     - Установка VictoriaMetrics
     - Установка Grafana
     - Настройка источника данных (VictoriaMetrics) в Grafana
     - Импорт предустановленных дашбордов
  5. Дополнительный playbook (по вашему усмотрению)
     - Например, для настройки сбора метрик с нод, интеграции с Prometheus Node Exporter или Telegraf и т. п.

**Требования:**
- ПО: Ansible
- Набор YAML-скриптов (плейбуков) для развёртывания и конфигурации
- Разделение плейбуков по компонентам

**Реализация:**
- Контейнер с Ansible

## Требования к инфраструктуре

### Базовые требования

**Docker-контейнеры:**
- Основа: образ на базе Debian
- Количество: 7 контейнеров (по одному на каждый элемент)
- Сетевое пространство: изолированная сеть Docker
- Преднастройки:
  - SSH-доступ для Ansible (ключи, пользователи)
  - Минимальные зависимости для установки ПО

**docker-compose.yml:**
- Поднимает все 6 контейнеров
- Настраивает сеть и порты
- **Не выполняет установку/настройку ПО** (только подготовка среды)

**Прочие требования:**
- Используемые образы: на основе Debian
- Prometheus и Grafana: официальные образы от разработчиков
- Все выложить в открытый GitHub репозиторий (или аналоги)

## Этапы реализации

### Этап 1: Развёртывание контейнеров

При запуске команды `docker-compose up` должны подняться 7 контейнеров в своем пространстве с соблюдением следующих условий:

- Контейнеры должны содержать ОС и преднастройки для доступа в них Ansible
- **Установка и настройка других компонентов на этом этапе ЗАПРЕЩЕНА**
- В инструкции должно быть отражено, как получить доступ в контейнер Ansible

### Этап 2: Автоматизированная установка и настройка

1. Получить доступ в контейнер Ansible
2. Запустить Ansible плейбуки для установки и настройки всех компонентов системы
3. По завершении плейбуков система должна быть полностью функциональна

---

## Функциональные требования после развёртывания

### 1. Балансировка трафика

При обращении по URL `http://<VIP_LB>:80` должна отображаться страница с контентом:
- "Бэкенд 1" или "Бэкенд 2" в зависимости от произведённой балансировки

**Проверка:**
```bash
curl http://VipLb:80
```
(должен вернуться текст "Бэкенд 1" или "Бэкенд 2")

---

### 2. Кластеризация балансировщиков

**Требования:**
- VIP-адрес принадлежит одной из нод (lb1 или lb2)
- При остановке активной ноды VIP переключается на резервную
- Система продолжает обслуживать запросы

**Проверка в инструкции:**
- Как узнать, на каком контейнере в данный момент находится VIP адрес
- Процедура проверки отказоустойчивости:
  1. Определить активную ноду с VIP:
     ```bash
     ip addr show | grep VIPLb
     ```
  2. Остановить активную ноду:
     ```bash
     docker stop lb1
     ```
  3. Убедиться, что VIP переключился на lb2 и запросы продолжают обслуживаться
  4. При обращении по `http://<VIP_LB>:80` приложение должно оставаться доступным

---

### 3. Мониторинг в Grafana

**Требования:**
- Grafana доступна по порту 3000
- Авторизация: логин/пароль по умолчанию (admin/admin)

**Датасорс:**
- Подключение к VictoriaMetrics
- Возможность просмотра всех собираемых метрик в разделе Explore

**Дашборд с предустановленными панелями:**

| Тип метрики | Назначение |
|------------|-----------|
| Статус балансировщиков | Отображение активного/резервного состояния (lb1 и lb2) |
| Доступность бэкенд-нод | Показатель работоспособности backend1 и backend2 |
| Нагрузка на ноды | CPU, RAM, сеть для всех компонентов |
| Состояние VIP-адреса | Информация о владельце VIP и его статусе |
| Статус-коды | Подсчёт HTTP статус-кодов (1xx, 2xx, 3xx, 4xx, 5xx) с балансировщиков |

**Рекомендуемые типы панелей:** Stat, Gauge, Time Series

## Инструкция по установке и проверке

### Развёртывание через Docker Compose

1. Клонировать репозиторий
2. Выполнить:
   ```bash
   docker-compose up -d
   ```
3. Убедиться, что все 6 контейнеров запущены:
   ```bash
   docker ps
   ```

### Доступ к контейнеру Ansible

1. Войти в контейнер:
   ```bash
   docker exec -it ansible /bin/bash
   ```
2. Перейти в директорию с плейбуками:
   ```bash
   cd /ansible
   ```

### Запуск Ansible-скриптов

Выполнить плейбуки в нужном порядке:

```bash
ansible-playbook playbook_lb.yml
ansible-playbook playbook_cluster.yml
ansible-playbook playbook_backend.yml
ansible-playbook playbook_monitoring.yml
```

### Проверка работы системы

**Проверить балансировку:**
```bash
curl http://VipLb:80
```
(должен вернуться текст "Бэкенд 1" или "Бэкенд 2")

**Проверить кластеризацию:**
1. Определить активную ноду с VIP:
   ```bash
   ip addr show | grep VipLb
   ```
2. Остановить активную ноду:
   ```bash
   docker stop lb1
   ```
3. Убедиться, что VIP переключился на lb2 и запросы продолжают обслуживаться

**Проверить мониторинг:**
1. Открыть Grafana: `http://<host>:3000`
2. Авторизоваться (логин/пароль по умолчанию: admin/admin)
3. Проверить дашборды и метрики
